# nevoice 实时识别 + 智能纠错改造计划

## 1. 背景与问题

- 当前实时识别链路存在两套实现：`nevoice/e-voice/server/routes/socketio_events.py` 只做简单的单段识别；`nevoice/e-voice/server/routes/ws.py` 虽实现了更复杂的会话管理，但缺少可靠的音频分片处理、说话人状态、二次纠错（2pass）与标点，且与 `RealtimeSpeechSession` 紧耦合，导致“实时字幕 + 智能纠错”表现不稳定。
- FunASR 的官方 demo（例如 `FunASR/runtime/python/websocket/funasr_wss_server.py`、`FunASR/runtime/docs/websocket_protocol_zh.md`）已验证了实时流式输出 + 句尾离线纠错的效果，可作为权威参考。
- **强制要求**：旧实时语音方案（`nevoice/e-voice/server/routes/socketio_events.py`、`nevoice/e-voice/server/routes/ws.py` 现有实现以及 `nevoice/e-voice/server/session.py`、`nevoice/e-voice/server/state.py` 等依赖文件）在新方案灰度完成后必须彻底删除，禁止继续维护双轨逻辑；所有实时能力需完全参考 FunASR 开源实现并遵循《nevoice/e-docs/SDK相关/接口文档/开放接口设计.md》的协议定义重新编写。
- 目标是：**在 nevoice 内重构实时语音识别逻辑，完全复刻 FunASR 2pass 架构**，实现语音输入法级别的低延迟流式输出与句尾精准纠错。

## 2. 目标能力

1. **单/多并发实时识别**：支持在线流式输出（`mode=online`），延迟 < 500ms。
2. **二次纠错 (2pass)**：语音结束（VAD 或客户端 is_speaking=false）后，自动触发离线 Paraformer 模型，结合标点/ITN 输出最终结果。
3. **智能热词/声纹**：沿用 `hotwords`、`speaker_id` 等增强字段，支持后续声纹匹配。
4. **协议对齐**：完全实现 FunASR WebSocket 协议（启动帧、音频帧、控制帧、在线/离线结果类型）。
5. **可观测性**：提供 request_id/session_id、延迟指标、缓存命中率、纠错触发率。

## 3. 现状差距

| 模块 | nevoice 现状 | FunASR 能力 | 差距 |
| --- | --- | --- | --- |
| 音频分片 | 依赖客户端 JSON 字段，自行拆解 base64 | 支持二进制帧 + 控制帧、chunk_interval 动态调整 | 缺 VAD 控制、chunk 缓冲策略 |
| 流式 ASR | `recognize()` 阻塞式调用 | `AutoModel` streaming 模型 (online Paraformer) | 缺 streaming pipeline 与缓存管理 |
| VAD/Punc/ITN | 通过 `RealtimeSpeechSession` 简单拼接 | VAD + Streaming ASR + Offline ASR + Punc + ITN 组合 | 缺模型链路与调度 |
| 二次纠错 | 手动 finalize，逻辑脆弱 | mode=`2pass-online` + `2pass-offline` 消息 | 缺统一协议与离线回调 |
| 代码结构 | Flask Sock 内部混排状态机 | FunASR 拆分为 session 状态+pipeline | 需要模块化改造与测试 |

## 4. 改造思路

### 4.1 目标架构

```
Client
   ↕  WebSocket (FunASR协议)
Flask Sock Endpoint (ws.py → 新 API)
   ↕  Session Manager (per connection)
Streaming Engine
   • VAD 模块 (FunASR AutoModel)
   • Online ASR (Paraformer online)
   • Offline ASR (Paraformer offline)
   • Punctuation + ITN
   • Text Merger（在线/离线融合）
Result Dispatcher
   ↕  Redis/Message Queue (可选)
```

### 4.2 迁移步骤

1. **协议层重写**
   - 在 `nevoice/e-voice/server/routes/ws.py` 中引入新的 `RealtimeAPI`，遵循 FunASR WebSocket 协议：客户端通过 JSON 控制消息设置 `mode/chunk_interval/hotwords`，音频以二进制帧发送，并输出《nevoice/e-docs/SDK相关/接口文档/开放接口设计.md》规定的消息体。
   - 旧版 `socketio_events.py`/`ws.py` 已移除，`register_ws_routes` 直接代理新实现，无需灰度。

2. **引入 FunASR Pipeline**
   - 新建 `nevoice/e-voice/speech_recognition/streaming/` 模块，封装 FunASR `AutoModel` 加载（online/offline/vad/punc），并与 FunASR demo 使用相同的模型组合与参数。
   - 参考 `FunASR/runtime/python/websocket/funasr_wss_server.py` 中的 `status_dict_*` 缓存，设计 `StreamingState` 数据类：包含 chunk 缓存、VAD 状态、is_final、segment_seq 等。
   - 提供 `StreamingEngine.push(audio_chunk, session_state) -> List[Event]`，事件包括 `partial_result`, `final_result`, `correction`，并确保所有事件字段满足《nevoice/e-docs/SDK相关/接口文档/开放接口设计.md》的定义。

3. **VAD + 纠错融合**
   - 实现 VAD 前后判定逻辑，与 `chunk_interval` 绑定。识别到 `speech_end` 后，将累积帧交给 offline ASR + Punc + ITN，生成 `2pass-offline` 结果。
   - 引入 `TextAccumulator`：维护 confirmed_text、candidate_text、revision_id，确保客户端能做增量渲染。

4. **线程与资源管理**
   - Streaming 模型保持长驻内存（GPU/CPU 自动选择），离线纠错可在独立线程池运行，避免阻塞在线推理。
   - session 超时（默认 60s 无输入）自动清理模型缓存。

5. **接口输出与观测**
   - 所有 WebSocket 下行消息统一格式：`{type, mode, text, segment_id, is_final, timestamps, latency_ms, request_id}`。
   - 在 `nevoice/e-voice/monitoring/` 中新增指标：`stream_latency`, `correction_latency`, `active_sessions`, `chunk_drop_count`。

6. **配置与运维**
   - 关键配置（模型 ID，chunk size，是否启用 2pass）写入 `nevoice/e-voice/config/realtime.yml`，支持热更新。

## 5. 实施计划（4 阶段）

| 阶段 |  关键交付 | 详细任务 |
| --- | --- | --- |

## 7. 规范与测试

- **编码规范**：Python 使用 Black + Ruff；新增模块必须具备类型注解与 docstring，日志统一使用 `loguru`（包含 `session_id`, `request_id`）。
- **单测**：模拟 `online`/`2pass` 模式下的 chunk 流，断言 partial/final 序列、纠错文本一致性。
- **集成测试**：复用 FunASR 客户端 (`FunASR/runtime/python/websocket/funasr_wss_client.py`) 指向 nevoice WebSocket，确保协议兼容。
- **性能**：压测脚本目标：单实例 ≥ 50 并发流、平均延迟 < 400ms、纠错延迟 < 2s。

## 8. 依赖与风险

1. **模型加载**：FunASR 在线/离线模型体积较大，需要预加载并与现有 `recognize()` 共存；需评估 GPU 显存或启用半精度。
2. **资源隔离**：若实时与离线服务部署在同一实例，需在进程内做线程/协程隔离，防止阻塞 REST 请求。
3. **协议升级**：客户端需同步升级（麦克风/浏览器 SDK）；需提供 TS/JS demo，避免集成成本。
